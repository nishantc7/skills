What you need to decide

Edge case · retry

01A charge that timed out may have gone through, and the retry charges again

// BEFORE
await httpClient.post("/v1/charges", body);

// AFTER — no idempotency key is sent
await httpClient.post("/v1/charges", body, { attempts: 3 });

The question

A timeout does not mean the charge failed. Does the provider reject a repeated charge that carries no idempotency key?

How I know

not checkedOnly the provider's docs were read. Nobody sent a repeated charge on staging.

This is wrong if

A customer on a slow connection is charged twice for one order.

The other option

Send an idempotency key built from the order id, so a retry cannot charge twice.

Further reading. Stripe's post "Designing robust and predictable APIs with idempotency" explains why a retried payment needs a key.

The question

The 10-second timeout now applies to each attempt, not to the whole payment. Is a 31-second wait acceptable at checkout?

How I know

read the codeThree attempts of 10 s, plus waits of 200 ms and 400 ms.

This is wrong if

Customers give up, reload the page and pay again while the first payment is still being retried.

The other option

Give the whole payment one 10-second budget, shared by all attempts.

Performance · outage

04In an outage, retries triple the traffic, and all at the same moments

// BEFORE — did not exist

// AFTER — httpClient.ts:38, the same wait for every caller
await sleep(200 * 2 ** attempt);

The question

With no random spread in the waits, every failed checkout retries at the same instant. Can a provider that is already failing take three times the calls?

How I know

not checkedNobody knows the provider's rate limit during an incident.

This is wrong if

A short provider hiccup becomes a long outage, because our retries keep it overloaded.

The other option

Add random jitter to each wait, and stop retrying after a run of failures.

Further reading. The AWS Builders' Library article "Timeouts, retries, and backoff with jitter" explains how retries can overload a failing service.

The ticket against the code

Silence is the finding. Where the ticket did not specify something and the code chose anyway, that choice is where a discussion would have happened if there had been time for one.

The ticket asked. Retry payment calls that fail with a timeout or a server error, so brief provider errors stop failing checkouts.

The code does. It retries payment calls, by adding retries to the shared HTTP client that 11 other callers also use.

The ticket did not say

  • Whether other requests retry too. The code makes all of them retry.
  • How a retry avoids a second charge. The code sends no key.
  • How long checkout may wait. The code allows about 31 seconds.
  • How many attempts. The code picked 3, from no measurement.
Smaller things I noticed
  • The wait times, 200 ms and 400 ms, are literals in the code, not settings.
  • The final error message dropped "please try again", so customers no longer know they can.
  • docs/payments.md still says a payment is sent once.
